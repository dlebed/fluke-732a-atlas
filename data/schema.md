# Dataset schema

A dataset is one board — or, for `SYS`, the system interconnect diagram treated
as a board. `data/<asm>.js` calls `BoardExplorer.register({...})` with the
object described here. It is generated by `tools/assemble.py` from the curated
files below; edit those, not the output.

The 732A Instruction Manual (P/N 645051, May 1983) is a 600 dpi scan with no
text layer, so there is no extraction step: every input is transcribed, checked
by a second reader, and kept under `data/`. `docs/manual/` holds the
transcriptions the values were read from, with page references.

| File | Owner | Holds |
|---|---|---|
| `data/<asm>.board.json` | **you** | `id`, `name`, `pca`, `pcb`, `drawingNo`, `rev`, `refs`, `layers`, `schematics` |
| `data/<asm>.parts.json` | **you** (two readers, diffed) | `components: [{ref, kind, desc, fluke, mfrCode, mfrPart, qty, notes, esd, star, page}]`, ranges expanded |
| `data/<asm>.procedures.json` | **you** | `procedures: [{id, title, source, prereq, warnings, steps}]` |
| `data/<asm>.testpoints.json` | **you** | `rails`, `testpoints`, `probePoints` — expected values and their citations |
| `data/<asm>.reference.json` | **you** | `overview`, `railCircuits`, `functions`, `faultCodes` (symptoms), `warnings`, `caveats`, `foreignStepRefs`, `tables` |
| `data/<asm>.caps.json` | **you** | which rail each capacitor sits on |
| `data/<asm>.coords.json` | `tools/build_coords.py` / Author Mode | positions — generated, never hand-edited |
| `data/<asm>.coords.overrides.json` | **you** | hand corrections over the readers, plus `confirm` |

`<asm>` is `a3`, `a4`, `a5` or `sys`. Every key beginning with `_` in a curated
file is a comment and is stripped by the build, so reasoning can be written
next to the value it explains.

---

## `board.json` — identity, drawing, sheets

```js
{
  "id": "A3",                              // uppercase, as the manual writes it; "SYS" for the interconnect
  "name": "Pre-Regulator PCB Assembly",
  "pca": "642264",                         // Fluke stock number of the assembly, from the parts table
  "pcb": "732A-1003",                      // etch number printed on the schematic title block
  "drawingNo": "732A-4003",                // assembly drawing number, as the figure caption prints it
  "rev": "B",                              // revision level this manual documents (Table 7A-1), if it says
  "refs": { "locator": "Figure 8-3", "schematic": "Figure 8-3 (cont)",
            "parts": "Table 5-4", "theory": "§3-…", "troubleshooting": "Table 4-3, §4-44" },
  "layers": [
    { "id": "drawing", "label": "Board drawing", "src": "assets/a3/drawing.png",
      "credit": "Figure 8-3, 732A Instruction Manual", "transform": "identity" }
  ],
  "schematics": [
    { "id": "sh1", "title": "Pre-Regulator", "src": "assets/a3/sch1.png", "figure": "8-3 (cont)",
      "grid": { "cols": ["8","7","6","5","4","3","2","1"], "rows": ["D","C","B","A"],
                "frame": { "x0": 0.02, "y0": 0.03, "x1": 0.98, "y1": 0.97 } } },
    { "id": "sh2", "title": "Interconnect", "src": "assets/sys/drawing.png", "figure": "8-1" }
  ]
}
```

`refs.locator` and `refs.parts` are printed in the page footer, so give them
text even on `SYS` ("none — items are what the diagrams draw" is fine).

**Layers.** Only the drawing exists today; it *is* board space and needs no
transform. The photo slot stays in the schema: a `photo` layer would declare a
3×3 homography `transform: { H: [ … 9 numbers … ] }` mapping board space onto
its own normalised image space, solved by `build_coords.py` from
`layers.photo.landmarks` in the overrides. With no photo layer the engine greys
out Photo / Overlay / Swipe and Author Mode says the board has no photograph.

**Sheets.** Figures 8-1 and 8-2 are shared: `SYS` owns them as its drawing and
`sh1`; each board names the same asset files again as its `sh2` (Interconnect)
and, on A3/A4, `sh3` (Motherboard, battery and LED PCBs). **`grid` is
optional.** The interconnect diagrams have no zone letters; a sheet without
`grid` simply has no zone anywhere — card, inspector, sheet tab — and nothing
derives one. A sheet that has a grid must give all three of `cols`, `rows` and
`frame` (the inner border of the zone grid in normalised sheet coordinates), so
zone labels like `sh1/C4` are derived from positions and never typed.

## Coordinates

Everything is authored in **board space**: `(0,0)` top-left to `(1,1)`
bottom-right of the board drawing. Positions are fractions, never pixels, so
they survive re-exporting the images at a different width. Sheets have their own
space, one per sheet.

**A marker's `x,y` is the box centre, not its top-left.**

### Provenance: `placement`

Every position records how it was arrived at, and the app says so rather than
presenting every marker as equally trustworthy:

| `placement` | Means |
|---|---|
| `verified` | placed by hand in the overrides, or a read position listed under `confirm` |
| `agreed` | several tesseract passes landed on the same spot |
| `single` | one pass found it, nothing corroborates it |
| `ambiguous` | passes disagreed — or the reader and the vision model did (see below) |
| `collision` | two designators claim the same spot |
| `vlm` | read by a vision model from the drawing; the reader had nothing. Confirm before trusting |

`build_coords.py` merges three sources in rising order of authority:

1. `.build/<asm>/ocr_<space>.json` — tesseract (`tools/ocr_designators.py`).
2. `.build/<asm>/vlm_<space>.json` — a vision model (`tools/vlm_place.py plan|merge`),
   shape `{"space":"board","image":{"w":W,"h":H},"entries":[{"ref":"C1","x":..,"y":..,"w":..,"h":..,"refined":true}]}`
   in pixels of that space's `_full.png`, `x,y` the box centre. A designator
   the reader did not place takes the model's box as `vlm`. One the reader did
   place keeps the reader's box unless the two disagree by more than a box
   width — then the model's box wins and the placement is `ambiguous` with a
   note, because one of them is on the wrong label and a person has to say which.
   `refined: false` (the box could not be snapped to the lettering) is carried
   as a `placementNote`.
3. `data/<asm>.coords.overrides.json` — wins over both.

### `coords.overrides.json`

Pixels of `.build/<asm>/drawing_full.png` for the board and of each sheet's own
`schN_full.png` for the sheets — *not* the images the browser loads. Do not
convert by hand; `tools/fold_overrides.py` folds an Author Mode export.

```js
{
  "imageSize": { "w": 3620, "h": 4552 },          // checked against the drawing at build time
  "sheetImageSize": { "sh1": { "w": 9440, "h": 5567 } },   // or one {w,h} for every sheet
  "board": {
    "TP5": { "x": 1210, "y": 3305, "w": 90, "h": 90, "shape": "point", "note": "on the pad" },
    "C1":  { "x": 640, "y": 1180, "w": 230, "h": 230, "shape": "circle", "fitted": true }
  },
  "schematic": { "sh1": { "TP5": { "x": 5620, "y": 2210, "w": 95, "h": 36 } } },
  "confirm": ["R7", "R8", "CR2"],                 // read positions checked by eye: placement -> verified, geometry unchanged
  "confirmSchematic": { "sh1": ["R7"] },          // the same, per sheet
  "drop": ["R31"],                                // a read that points at another part's label
  "dropSchematic": { "sh1": ["R31"] },
  "notOnDrawing": ["MP1", "MP2"],                 // no silkscreen designator exists
  "schematicSheetRule": { "threshold": 100, "below": "sh1", "atOrAbove": "sh2", "exceptions": {} },
  "sheets": { "sh1": { "grid": { … } } },         // a zone grid measured in Author Mode
  "layers": { "photo": { "landmarks": [ { "src": [x, y], "dst": [x, y] } ], "approximate": true } }
}
```

**A sheet placed only by hand is still built.** The interconnect sheets are
simplified diagrams nobody runs a reader over, and test points are placed by
hand as a matter of course, so a sheet that appears only under `schematic`,
`confirmSchematic` or `dropSchematic` is picked up without any `ocr_shN.json`
or `vlm_shN.json`. Its size comes from the `schN_full.png` crop when it is
there, else from `sheetImageSize`; with neither, the build stops and says so.

**`confirm`** is the review loop's cheap path. `review_markers.py` renders a
tier; every marker that sits on its own label goes into `confirm` by name, and
the build marks it `verified` without anyone retyping a box. A designator may
not be both confirmed and dropped or hand-placed in the same file — the build
refuses. Confirming something nothing placed is a warning, not an error.

### Marker shape

| `shape` | Drawn as | Used for |
|---|---|---|
| `rect` | rounded rectangle | the default; the box is the designator lettering |
| `circle` | ellipse inscribed in the box | a part whose body is a circle on the drawing |
| `point` | circle of the box's shorter side | test points and probe pads |

A shape is a claim about the geometry, not a decoration, so it is only
meaningful on a hand-placed body box; the readers place lettering and their
boxes are always `rect`. Test points are placed by hand on the pad, `shape:
point`, as a matter of course. An overrides entry may also carry `"fitted":
true` to record that the box was measured by `tools/detect_round_parts.py` and
then checked by eye rather than typed; the build ignores it.

## Components

From `parts.json`, plus geometry and a `function`:

```js
{
  ref: 'C1', kind: 'cap',
  desc: 'CAP, ELECT, 100 UF +75/-20%, 80V',     // as printed in the parts table
  function: 'Filters the rectified raw supply', // reference.json functions[ref], when §3 says
  fluke: '381939', mfrCode: '89536', mfrPart: '381939', qty: 1,
  notes: '…', esd: true, star: true,           // star: the Table 5-6 asterisk — return to Fluke / replace the PCB
  page: 54,                                    // PDF page the row was read from
  board: { x, y, w, h, shape },
  sch: [ { sheet: 'sh1', x, y, w, h, zone: 'C6' } ],   // zone only where the sheet has a grid
  verified: true, schVerified: true,
  placement: 'verified' | 'agreed' | 'ambiguous' | 'single' | 'collision' | 'vlm',
  placementNote: '…',
  notOnDrawing: true,                          // no silkscreen designator exists
  link: { assembly: 'A3', ref: 'TP1' }         // see Links
}
```

`kind` drives the marker colour and the type legend: `cap`, `res`, `diode`,
`zener`, `transistor`, `ic`, `resnet`, `fuse`, `relay`, `switch`, `thermistor`,
`varistor`, `connector`, `mech`, `part`, `inductor`, `transformer`, `crystal`,
`socket`, `wire`, `led`, `battery`, and the two this instrument added:
`terminal` (E — harness feed-through and solder terminals) and `heater` (HR —
the oven heaters). On the 732A `J` and `P` are both connectors, not jumpers.
`parts.json` names the kind per row; `ocr_designators.py` accepts these
prefixes: `CR VR RT MP TP DS FL XF BT HR C R Q U Z F J K H P S W T E`.

Every value `null`, `false` or `""` in a `parts.json` row is dropped from the
output, so a row need only say what is true.

**`SYS` items** are what Figures 8-1 and 8-2 draw: the assembly blocks (A3,
A4, A5, A6, A1, the front panel), the connectors, the battery pack parts, the
oven heaters and thermistors and the front-panel LEDs. Refs are prefixed by
their assembly (`A6BT1`, `A1DS2`, `A2J3`) so nothing collides with a board's
own designators. The assembly blocks carry a `link` to their dataset.

## Three small flags

`board.json` may carry `virtual: true` — a diagram rather than a board anyone
pulls from the instrument (SYS); the log's fitted-board list and the service
report skip it. A part may carry `aliases: ["VR1"]` — names the errata or a
figure use for the same designator; search matches them and the card says
which is which. A table in `reference.json` may carry `headerRow: true` when
its first row is the column heading; otherwise the row keys are the headings.

## Links

An item — component, test point or probe point — may carry

```js
link: { assembly: 'A3', ref: 'TP1' }     // ref optional
```

The card shows *Open A3 ›* (label from the target dataset's id and name);
pressing it switches the assembly picker to that dataset and, if `ref` is given
and exists there, selects and focuses it. `assemble.py` passes `link` through
untouched. `check_data.js` requires `link.assembly` to exist as
`data/<id>.js` (file name matched case-insensitively) and `link.ref`, when
given, to be a designator on it.

## Test points

A test point is both a parts-table line and an expectation. Five forms of
expectation exist because the manual uses all five:

```js
{ nominal: 32, tolerance: 1.6 }        // 32 V ±1.6 V
{ nominal: 10, tolerancePct: 0.001 }   // 10 V ±0.001 %
{ nominal: 0, maxAbs: 1.0 }            // "less than 1.0 V" either sign
{ max: 60 }                            // ≤ 60 V          (one-sided)
{ min: 24 }                            // ≥ 24 V          (one-sided)
{ min: 24.5, max: 26.5 }               // +24.5 … +26.5 V (two-sided band)
```

`min`/`max` are numbers in the point's `unit`. For `{min, max}` the nominal is
the midpoint and the tolerance half the width; for a one-sided limit the
nominal is the bound itself and a reading within 5 % of it is *marginal*
rather than a pass. `min >= max` is an error.

```js
{
  ref: 'TP6', signal: 'PRE-REG OUT', rail: 'PREREG', kind: 'testpoint',
  refPoint: 'TP4',                   // where the meter's low lead goes
  nominal: 32, tolerance: 1.6, unit: 'V',
  inferred: true,                    // Table 4-3 gives no tolerance; this one is assumed
  condition: 'Line power, battery charged',
  source: 'Table 4-3, §4-44 step 18',// required: every value cites its origin
  isReturn: false,                   // a return carries no expectation
  noPublishedValue: true,            // the manual tabulates none (A5 TP1–TP14, §4-53)
  notInParts: true,                  // real probe target with no parts-table line (front-panel posts)
  conflict: '…',                     // where two sources disagree, and which won
  hazard: 'MAINS',
  onFail: ['CR1', 'C1'],
  link: { assembly: 'A3', ref: 'TP6' },
  board: {…}, sch: […]
}
```

Where a point has no single correct reading it carries `states` instead, and
each state is a complete expectation with its own `label`, `setup`, `source`
and `onFail` — A3's charger output is one value with BTRY CHG lit and another
with it out.

`probePoints` are the same shape but identified by `id` rather than `ref`, for
measurements the manual calls for at a component pin ("the cathode of CR5").

## Rails, procedures and symptoms

```js
rails: {
  'PREREG': { label: 'Pre-regulator output', com: 'TP4', color: '#5ec2a8',
              circuit: { rails, rectifier: [], filters: [], regulators: [], tps: [], note, source } }
}                                    // display record from testpoints.json, circuit from reference.json railCircuits

procedures: [ { id: '4-44', title: 'Battery Charger Adjustment', source: '§4-44',
                prereq: '…', warnings: ['…'],
                steps: [ { n: 1, text: '…', refs: ['TP5', 'R20'],
                           measure: [ { point: 'TP5', ref: 'TP1', nominal: 33.0, tolerance: 0.1, unit: 'V' } ] } ] } ]

faultCodes: [ { code: 'S3', title: 'BTRY CHG indicator never lights',      // the symptom
                measure: 'Charger output missing',                          // probable cause
                verdict: 'Check TP2 against TP1; then Q3, CR4',             // action
                refs: ['TP2', 'Q3', 'CR4'], source: 'Table 4-2' } ]
```

`faultCodes` is rendered as the **Symptoms** tab (Table 4-2); the key keeps its
name because the engine renders the same array. `measure` is shown as *Probable
cause* and `verdict` as *Action*; `verdict` is required.

A step's `measure` is optional: where present it is a list of expectations
(`point`, optional `ref` for the low lead, then any expectation form above) the
step asks for, so the step can put readings into the log without parsing prose.

**`foreignStepRefs`** in `reference.json` names, per step, designators that
belong to another assembly so no clickable chip is offered for them: keyed by
step number for every procedure on the board (`"12": ["TP6"]`), or by procedure
id and then step (`"4-44": { "12": ["TP6"] }`) when the board has more than
one. A caveat should say why the link is absent.

**`tables`** in `reference.json` is a list of `{ title, source, rows: [ {…} ], note }`
shown verbatim; the renderer is generic over the row keys.

**`warnings`** (shown at the top of procedure mode) and **`caveats`**
(`{ title, text, refs, source }` — source disagreements and assumptions worth
knowing about, such as "the interconnect diagram is simplified" and "Table 4-3
tolerances are assumed") both come from `reference.json`.

## Capacitors

`caps.json` holds `caps: { 'C1': { rail, appliedV, source: 'schematic' | 'inferred', note } }`
— the rail each electrolytic or tantalum sits on, traced on the sheet, and the
voltage across it: from Table 4-3 where published, else inferred with the
reasoning in the note, else `null`. The rated voltage is read from `desc` at run
time. A capacitor that comes out above its own rating is an error in the data,
not a finding.

## Invariants

`node tools/check_data.js <asm>` (or `all`) enforces these, and fails the build
if any break:

- designators are unique
- every `refPoint` and every `rails[*].com` resolves to a real test point
- a point that is neither a return nor `noPublishedValue` carries an
  expectation (one of `nominal`, `maxAbs`, `min`, `max`), cites a `source`, and
  a nominal has a tolerance
- `min` and `max` are numbers, and `min < max` where both are given
- a point marked `isReturn` or `noPublishedValue` carries no expected value
- every ref named in `onFail`, a procedure step, a step's `measure`, a symptom
  or a rail circuit exists on the board
- every `link.assembly` exists as a built dataset and `link.ref` is on it
- positions lie within `0..1`, on the board and on every sheet
- every `sch[].sheet` names a declared sheet; a sheet with a `grid` has
  `cols`, `rows` and `frame`

It also reports, without failing, items still unplaced and markers sitting
entirely inside another marker — each of those gets looked at.

## Pipeline

```
tools/extract_assets.sh <asm>          PDF page -> .build/<asm>/*_full.png, assets/<asm>/*.png
tools/ocr_designators.py <asm> <space> tesseract -> .build/<asm>/ocr_<space>.json
tools/vlm_place.py plan|merge <asm> <space>   vision model -> .build/<asm>/vlm_<space>.json
tools/build_coords.py <asm>            ocr + vlm + overrides -> data/<asm>.coords.json
tools/assemble.py <asm> | all          curated + coords -> data/<asm>.js
node tools/check_data.js <asm> | all
tools/review_markers.py <asm> <space> --tier vlm       look, then confirm/drop/override, rebuild
tools/fold_overrides.py / fold_bundle.py               Author Mode exports -> overrides
tools/make_release.sh                  -> dist/fluke-732a-atlas.zip
```

`data/<asm>.js` and `data/<asm>.coords.json` are output. An Author Mode export
folds through the overrides or it does not last.
